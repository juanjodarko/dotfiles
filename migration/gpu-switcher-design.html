Hybrid GPU switcher — design & the driver blocker

A quality-of-life way to flip the NVIDIA dGPU on for the occasional road-trip game and back off for battery — designed against your real hardware (Razer Blade, Intel HD 630 + GTX 1060 Mobile), your existing supergfx read-layer, and the planned Quickshell GPU widget. Usage target: off by default, Hybrid now and then.

Razer Blade · Kaby Lake-H dGPU GTX 1060 Mobile (Pascal, 10de:1c20) supergfxctl 5.2.7 modes: Integrated / Hybrid / NvidiaNoModeset driver: nvidia-open 610 ⚠
⛔ Planning only — nothing implemented.

This is a design + a flagged blocker. No driver, config, or system change has been made. The driver fix in §0 is a real-laptop graphics-stack change → strictly gated (VM/careful, your explicit go-ahead), per the migration guardrails.

§0Blocker first: your dGPU almost certainly can't initialize right now

blocker GTX 1060 (Pascal) + nvidia-open = no working driver

You have only nvidia-open 610.57.04 installed (no proprietary nvidia, no legacy branch). The open kernel modules require a GSP processor, first shipped in Turing — Maxwell/Pascal/Volta are not supported by the open module, and NVIDIA's 590 release dropped Pascal from the main packages. Your GTX 1060 is Pascal (GP106). So in Hybrid mode the dGPU won't bind/initialize — no CUDA, no game offload. You likely haven't noticed because you live in Integrated (dGPU removed, so nvidia-smi is expected to be silent there anyway).

The fix — switch to the legacy proprietary branch

Replace nvidia-open/nvidia-utils with the last Pascal-capable proprietary branch, available in the AUR: nvidia-580xx-dkms + nvidia-580xx-utils + lib32-nvidia-580xx-utils (currently 580.178.04; the lib32 one is needed for Steam/Proton). Trade-off: it's a frozen branch — no new features, and DKMS can eventually break against very new kernels, so it becomes a thing to watch on updates.

Verify in one step (after the swap): switch to Hybrid, log out/in, then nvidia-smi -L should list the GTX 1060. Until that prints the card, no switcher is worth building.

blocker B A rogue leftover also disables the dGPU

Separately, /etc/modprobe.d/system76-power.conf — an orphaned, unowned leftover from the uninstalled system76-power tool — does alias nvidia off and blacklists the modules, so nvidia can never load even with the right driver. It must be removed too. (Your supergfxd.conf is fine — supergfxd manages it; nvidia-pm.conf's NVreg_DynamicPowerManagement=0x02 is a Turing-only no-op on Pascal, optional to drop.)

Confidence on Blocker A: high (architectural — the open module fundamentally can't drive pre-Turing), but not watched succeed live, since confirming needs a Hybrid logout on the real laptop. Both fixes + verification are written up as an exact, gated runbook: migration/nvidia-580xx-migration.md.

§1Mode reality — what each supergfx mode actually gives you

ModedGPUCUDA / LLMGamesSwitch costBattery
Integratedoff, removed from bus ✗ gone✗ logout to leavebest — your default
Hybridon; idles ~10–15 W (Pascal can't RTD3) ✓ directly, no prime-run✓ via prime-run logout to enterworst
NvidiaNoModesetoff (same removal as Integrated) ✗✗ live, but needs nvidia-drm.modeset=0n/a — not useful here
  • Your flow is Integrated ⇄ Hybrid, and each direction is a logout (a Wayland-session restart, not a reboot). Confirmed from supergfxctl source; there's no live path on this non-mux Razer.
  • Pascal can't idle cheaply. Fine-grained runtime power-down (RTD3/D3cold) is Turing+ only, and it also wants a Coffee-Lake-or-newer host — your Kaby Lake fails on both counts. So "just stay in Hybrid" is not a battery option; the real off-switch (Integrated) is genuinely needed. This is exactly why your "keep it off" instinct is right.
  • NvidiaNoModeset is a red herring for you: it switches live but it's a power-off state (no CUDA/games), and it isn't even offered because you boot with nvidia-drm.modeset=1 (which you want for Wayland). Ignore it.
  • LLM work = Hybrid, no prime-run. prime-run only sets GL/Vulkan offload env; CUDA (ollama, llama.cpp, PyTorch) sees the card directly once it's powered. Games need prime-run (render offload).

§2The design — one backend, two surfaces (reusing what you already built)

You already have the hard half: gpu-mode-check.sh (mode→state) and gpu-mode-monitor.sh (watches supergfxd's D-Bus NotifyGfx signal) + its user service. The switcher just adds a write path and a UI surface — mirroring the theme-switcher's "headless backend + thin frontends" shape.

┌─────────────────────────────────────────────┐ │ gpu-mode-set <Integrated|Hybrid> (headless) │ ← new; the one write path │ • validate mode │ │ • confirm (logs you out!) │ │ • supergfxctl -m <mode> │ │ • notify-send "log out to apply" │ └───────────────┬───────────────────────────────┘ reads state via │ ▲ both surfaces call the SAME backend gpu-mode-check.sh │ │ ┌───────────────┴────┐ ┌───┴───────────────────┐ │ waybar custom mod │ │ Quickshell GPU widget │ │ (NOW — fast win) │ │ (LATER — planned QML) │ │ icon + on-click → │ │ same click→menu │ │ menu → gpu-mode-set│ │ io.github…gpu-mode │ └─────────────────────┘ └───────────────────────┘ change events ← gpu-mode-monitor.sh (D-Bus) refresh both surfaces live
  • Backbone — gpu-mode-set: a headless script (same pattern you'll use for theme-set). Validates the target mode, shows a confirm (because it logs you out), calls supergfxctl -m, then notifies. Both UIs call it — no logic duplicated.
  • Surface A — waybar module (now): icon driven by gpu-mode-check.sh; on-click opens a small menu (wofi/rofi/Vicinae) → confirm → gpu-mode-set. Fastest QoL; you already run waybar. Crib theo-donacik/supergfxctl-waybar-module.
  • Surface B — Quickshell widget (later): this is your roadmap's "first QML plugin" (io.github.juanjodarko.gpu-mode), upgraded from indicator → interactive toggle. Same backend, nicer surface; lands with the standalone bar.
  • Game step: once in Hybrid, launch with prime-run <game> (Steam: set launch option prime-run %command%). Optional: wrap with gamemode/gamescope.
  • Robust capability detection (avoid Omarchy's bug, below): decide "is this machine hybrid-capable?" from the supergfx mode name (your gpu-mode-check.sh already does this), not from counting live PCI devices — in Integrated the dGPU is gone from the bus, and a PCI-count check would make the toggle vanish exactly when you need it to switch back.

§3The everyday flow — "off by default, a game on the road"

  1. Default: Integrated. Bar shows a subtle iGPU glyph. Zero dGPU draw.
  2. Want to game: click the indicator → "Enable NVIDIA (Hybrid) — will log you out" → confirm → gpu-mode-set Hybrid → notify "Save work & log out to activate." You log out/in.
  3. In Hybrid: bar switches to a dGPU glyph with a battery-warning tint (reminder it's costing power). Launch the game with prime-run.
  4. Done: click → "Disable NVIDIA (Integrated)" → confirm → gpu-mode-set Integrated → log out/in → back to iGPU, best battery.
UX refinements that matter for the occasional/on-the-road pattern
  • Always confirm — the switch logs you out; you never want that by a stray click mid-work.
  • Post-login nudge — on first login in Hybrid, a notification "NVIDIA is ON (higher battery use) — revert when done" with a one-click back-to-Integrated action, so you don't forget and drain the battery.
  • Make "return to Integrated" as prominent as "enable" — for a road pattern, getting back to off is the action you'll want most.

§4What to crib, and what to watch

  • Crib (waybar): theo-donacik/supergfxctl-waybar-module — mode display + click-to-switch via supergfxctl; closest ready-made starting point.
  • Mirror (logic): Omarchy ships omarchy-toggle-hybrid-gpu (supergfxctl Hybrid↔Integrated). But note its bug (#5428): its capability check counts live PCI devices, so once in Integrated the toggle disappears and you can't switch back from the menu. Your gpu-mode-check.sh keys off the mode name and already avoids this — keep it that way.
  • Watch (future, maybe better): supergfxctl is now deprecated / its GitLab archived. It still works, but Omarchy is evaluating cardwire (eBPF + LSM hooks) as the successor — it can block/unblock the dGPU without a logout or reboot and stop background apps from waking it. If live, logout-free switching is worth it to you later, cardwire is the thing to evaluate. Not today (new/unproven; would replace supergfx).
  • No ready GUI applies: rog-control-center is ASUS-only; optimus-manager-qt is X11-only; envycontrol is CLI + reboot; switcheroo-control's "discrete GPU" launcher is GNOME-only and broken on Wayland+NVIDIA. Building the small custom module is the realistic path.

Honest bottom line

The switcher is a small, clean build on top of what you already have — but its whole point is a working dGPU, and right now the driver almost certainly isn't. Do §0 first (or decide the GTX 1060 stays dark and this feature is shelved). Given "off by default, occasional game," the target design is deliberately minimal: a confirmed, logout-aware Integrated⇄Hybrid toggle with a strong "get back to off" affordance — not live per-app juggling.
