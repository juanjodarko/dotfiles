§2The headline question: do you still need the "split-screen" plugin from hyprpm?

Three-part answer

(1) It isn't from hyprpm anymore. Your log confirms it loads as a Lua require() package, not a compiled .so. The hyprpm bits (permission = …hyprpm…, exec-once = hyprpm reload -n) live only in the dead hyprland.conf — you have zero hyprpm plugins.
(2) Yes, you still need the plugin's job. Hyprland 0.56 still has no native "each monitor owns its own independent workspaces 1–10." Native workspace rules only do static binding (workspace = 1, monitor:eDP-1) — not the dynamic per-monitor sets you rely on.
(3) You're on the right version of it. Keep it exactly as-is.

What "split-monitor-workspaces" actually does — and its status

  • Gives each monitor its own set of workspaces (key ALT+1 acts on the focused monitor's set, independently numbered). This is workspace isolation, not window "split-screen" tiling.
  • Alive & maintained: repo moved Duckonaut → zjeffer/split-monitor-workspaces (old URL 301-redirects). 788★, last commit 2026-08-23, release/0.56.x branch tracks Hyprland 0.56.x. Your v0.56.0 matches your 0.56.2 correctly.
  • You're on the surviving path. It's now a pure-Lua package; the old C++ .so is deprecated and dropped at Hyprland 0.57.0. You already migrated off it — future-proof.
  • hy3 interop: it auto-detects hy3 and uses hy3's dispatchers — so if you ever adopt manual tiling, this is the safe pairing.

Alternative considered — hyprsplit (shezdy)

Same job, also a Lua library, actively maintained (314★). Keys workspaces by monitor ID, recovers windows on monitor hotplug, has a swap-all-windows-between-monitors dispatcher. No reason to switch: you're on the more popular, hy3-compatible option. Only reconsider if you hit multi-monitor hotplug bugs.

Verdict keep as-is

Keep split-monitor-workspaces on release/0.56.x, loaded as a Lua package. On a major Hyprland bump (e.g. 0.57), the only maintenance is re-pointing that one branch — a one-line pull, not an ABI rebuild. This is the lowest-maintenance, highest-correctness setup available; the whole "should I still run this?" worry is a non-issue.

§6The plugin landscape — what's worth the rebuild tax

The core trade-off: Lua packages (like your split-monitor) survive Hyprland updates; hyprpm .so plugins are ABI-locked and must be rebuilt via hyprpm update on every Hyprland upgrade — and a plugin that lags a release can stall your whole upgrade. On a stability/dotfiles path, cosmetic .so plugins are a bad trade.

Plugin philosophy for a stability path

Keep exactly what you have. Prefer Lua-package plugins over .so. Only take on a heavyweight .so (hyprexpo/hy3/hyprscrolling) when it changes your actual workflow, never for looks — and rebuild them with hyprpm update on every Hyprland bump. Resist cosmetic creep.

§7The real clock: hyprlang → Lua

The version number isn't the pressure — the config language is. hyprlang (.conf) was deprecated in 0.55 and is expected to be dropped around 0.57/0.58; new features land in Lua only. You've already migrated, so you're ahead of the curve. The flip side:

  • The Lua hl.* API is young and still changing with no stability guarantee — 0.56 alone added a batch of helpers. Expect occasional breakage across major releases; keep an eye on release notes.
  • Because a Lua error aborts the whole file (see H2), a rollback path matters — which is the honest argument for keeping hyprland.conf around, but clearly marked as dead/rollback, not looking live.
  • Net: your migration decision was correct and early. The maintenance shifts from "chase deprecations" to "occasionally track Lua-API changes."

§8Flagged — separate from this planning

diagnosed The EGL error is benign log noise — no action required

The log repeats aquamarine [EGL] eglQueryDevicesEXT … EGL_BAD_ALLOC … Failed to allocate device list (6×/boot). Root cause, proven with a compiled EGL probe: your laptop is hybrid Intel iGPU + NVIDIA dGPU, currently in supergfx Integrated (dGPU off, no nvidia kernel module, only Intel on the bus). nvidia-utils registers the NVIDIA EGL vendor (10_nvidia.json); glvnd's libEGL dispatches eglQueryDevicesEXT to every vendor, and the NVIDIA ICD — GPU powered off — fails to allocate its device list and reports BAD_ALLOC through the EGL_KHR_debug callback aquamarine registers. The aggregate call still succeeds with mesa's 2 devices; Hyprland renders on Intel renderD128. Zero functional impact.

Options: (1) leave it — cosmetic, recommended. (2) Silence it only in Integrated mode via __EGL_VENDOR_LIBRARY_FILENAMES=…/50_mesa.json in the session env — but it must be conditional on supergfxctl -g (forcing mesa-only would hide the NVIDIA EGL device and break dGPU prime-offload in Hybrid mode), so it's a small script, not a hard-coded line. Repro/fix verified; probe is throwaway.
